## 1. 📂 지시서의 다이어트: "미니멀리즘 아키텍처"

과거에는 모든 규칙을 상세히 적는 것이 유행이었으나, 2026년의 정설은 **"적을수록 강하다(Less is More)"**입니다.

- **줄 수 기준 (날짜별로 다르게 관측됨):**
  - 다이제스트 2/28: "권장 최대 30줄" (ETH Zurich 연구 기준)
  - 다이제스트 3/1: "50~100줄" (AgentBench 138 태스크 기준, 초과 시 20%+ 저하)
  - 다이제스트 3/2: "150줄 이하" (초과 시 지시 무시 또는 API 오류)
  - **실용 기준: 100줄 이하를 목표로, 매 줄이 없으면 에이전트가 실수하는지 테스트**
- **당연한 것 삭제:** 모델이 이미 학습한 일반적 모범 사례나 폴더 구조 설명은 지우세요.
- **실패 기반 규칙 (`NEVER` / `MUST`):** "절대 하지 말아야 할 행동"과 "반드시 지켜야 할 아키텍처 결정사항" 위주로 기술하세요.
- **2단계 분리 구조:**
  - **전역 지시서 (`~/.claude/CLAUDE.md`):** 에이전트의 페르소나, 코딩 철학(예: "항상 가역적인 변경 우선"), 자주 쓰는 라이브러리 선호도.
  - **프로젝트 지시서 (`./CLAUDE.md`):** 해당 프로젝트의 빌드/테스트 명령어, 현재 작업 중인 기능의 핵심 포인터.

> **주의 — `/init` 자동생성 함정:** Cursor, Claude Code의 `/init` 명령으로 자동 생성된 `AGENTS.md`/`CLAUDE.md`는 "모든 시나리오에 유용한 것들"로 파일을 채워 오히려 성능을 저하시킵니다. Addy Osmani (Google Chrome 팀): *"Stop Using /init for AGENTS.md"* — 직접 작성하거나 최소한 자동 생성 후 90% 이상 삭제하세요.

## 2. 📝 "Vibe-First, Spec-Refined" (SDD와의 결합)

순수 바이브코딩의 속도와 명세 주도 개발(Spec-Driven Development, SDD)의 정확성을 결합한 하이브리드 워크플로우입니다.

1. **Vibe Phase:** "이런 느낌의 대시보드를 만들어줘"라고 던져서 빠르게 UI 초안과 기본 로직을 뽑습니다. (10x 속도 우위)
2. **Spec Phase:** 초안이 나오면 에이전트에게 `spec.md` 파일을 작성하게 시킵니다. 여기에는 **데이터 모델, 인증 로직, 에러 처리 전략, 성공 기준(Test Cases)**이 포함됩니다.
3. **Engineering Phase:** 확정된 `spec.md`를 '진실의 원천(Source of Truth)'으로 삼아 에이전트가 실제 코드를 구현하고 테스트를 통과하게 만듭니다.

> **왜 Spec이 필수인가:** 스펙 없이 진행하면 **아키텍처 결정의 이유(Why)**가 코드 어디에도 남지 않습니다. 코드베이스 자체가 유일한 진실이 되지만, 코드는 *왜* 그 결정을 했는지 설명하지 못합니다 — 이것이 "3개월 벽"의 핵심 원인입니다.

**어디에 적용할지 구분하기:**
- **Vibe로 해도 되는 것:** 프로토타입, UI 스캐폴딩, 반복 코드, 개인 프로젝트
- **반드시 SDD로 전환해야 하는 것:** 인증/인가 로직, 결제, 프로덕션 배포, 규제 산업 코드

## 3. 🤖 계층형 에이전트 팀 (Agent Teams)

하나의 에이전트가 모든 것을 처리하는 '플랫 스웜' 구조는 조율 오버헤드로 인해 실패하기 쉽습니다. **허브-앤-스포크(Hub-and-Spoke)** 구조를 설계하세요.

- **Researcher:** 기존 코드베이스와 문서를 분석하여 구현 가능성을 타진하고 보고서를 작성합니다.
- **Implementer:** Researcher의 보고서를 바탕으로 실제 코드를 작성합니다. 격리된 컨텍스트를 제공하여 오염을 방지합니다.
- **Tester/Reviewer:** 구현된 코드를 실행하고, 린터와 테스트 결과에 따라 Implementer에게 수정을 요청합니다.
- **Human-in-the-Loop:** 인간은 '계획 승인(Planning Gate)'과 '최종 커밋 승인' 단계에서만 개입하여 효율성을 극대화합니다.

> **플랫 스웜(Flat Swarm) 금지:** 조율 오버헤드로 86%가 복잡성만 추가. 거버넌스 없는 에이전트 체인은 **보안 취약점이 전파**될 위험이 있습니다.

## 4. 🧠 효율적 컨텍스트 관리 (Context Management)

대규모 코드베이스를 다룰 때 에이전트가 "불필요한 정보"에 오염되지 않게 관리하는 것이 핵심 역량입니다.

- **압축 포인터 (Compressed Pointers):** 수백 쪽의 문서를 다 읽히는 대신, 핵심 내용만 요약하거나 인덱싱된 포인터 파일(예: `docs_summary.md`)을 참조하게 하세요. (40KB → 8KB 압축으로 eval 통과율 100% 달성 사례)
- **3계층 메모리:**
  1. **세션 단기 메모리:** 현재 채팅 내의 문맥.
  2. **프로젝트 영구 메모리:** 프로젝트별 누적 레슨(교정 패턴 저장).
  3. **전역 레슨 로그:** 다른 프로젝트에서도 활용할 범용적 노하우.
- **동적 주입:** 정적 파일에 제약을 적어두는 대신, IDE의 레포 스캔 기능을 통해 필요한 컨텍스트만 실시간으로 주입하세요.

> **컨텍스트 오염 경고 — "새 채팅으로 시작하라":**
> 긴 채팅 히스토리는 AI 혼란과 환각의 주요 원인입니다. AI가 파일명을 잘못 변경하거나 관계없는 오류를 공유하기 시작하면, **지체하지 말고 새 채팅을 시작**하세요. 대화 히스토리 전체를 전달하는 것보다 "완료 단계 / 현재 단계 / 남은 단계" 상태 요약을 매 호출에 prepend하는 것이 더 효과적입니다. 이 처리 없이 방치하면 에이전트가 완료된 단계를 환각하거나 작업을 중단하는 현상이 20~30%의 확률로 발생합니다.

## 5. 📈 복리식 엔지니어링 (Compounding Engineering)

AI가 짠 코드는 언제나 '주니어 개발자의 초안'으로 대우해야 합니다.

- **TDD (Test-Driven Development) 루프:** "테스트를 먼저 짜고, 그 테스트가 통과될 때까지 코드를 수정해"라는 지시를 기본 워크플로우로 삼으세요.
- **자동화된 검증:** `ruff`, `mypy`, `vitest` 등의 도구를 에이전트가 직접 실행하고 결과를 해석하게 하여 자가 교정(Self-healing) 루프를 만듭니다.
- **자기개선 로직:** 에이전트에게 오류 로그를 자동으로 저장하고, 다음 작업 시 이를 참고하여 같은 실수를 반복하지 않게 설계하세요.
- **공격적 CI 필수:** AI 생성 코드의 약 15%가 버그를 포함합니다. CI/CD 없이 배포하는 것은 시한폭탄입니다.

> **diff 라인-by-라인 검토:** 에이전트 결과를 검토 없이 복붙하는 것은 프로덕션 취약점의 가장 흔한 경로입니다. 전문가는 반드시 diff를 직접 읽습니다.

## 6. 💡 전문가를 위한 실전 팁

- **ALL CAPS의 힘:** 에이전트가 자꾸 어기는 규칙은 **대문자(ALL CAPS)**로 강조하세요. 이행률이 비약적으로 상승합니다.
- **자유 에이전트 (Free-range):** 상세한 구현 방법(How)까지 제약하면 품질이 떨어집니다. 결과물의 형태(What)와 제약 사항만 명확히 준 뒤 방법은 에이전트에게 맡기세요.
- **MCP (Model Context Protocol) 활용:** 로컬 파일, DB, 외부 API를 표준화된 MCP 서버로 연결하여 에이전트의 도구 활용 능력을 극대화하세요. 단, **쓰기·삭제 작업은 반드시 사용자 승인 게이팅** — MCP 보안의 기본 원칙입니다.
- **가역적 행동 우선:** 에이전트에게 "언제든 되돌릴 수 있는(Reversible) 변경을 먼저 제안하라"고 지시하여 안전성을 확보하세요.
- **커밋을 자주:** GitHub에 작업 단위로 자주 커밋하세요. AI가 10개를 망가뜨려도 되돌아갈 수 있어야 합니다.

## 7. 🔒 바이브코딩의 4대 보안 함정

바이브코딩 앱의 보안 취약점은 **AI가 빠른 데모를 위해 보안 로직을 단순화하는 경향**에서 비롯됩니다.

### 함정 1: 노출된 API 키와 시크릿
- AI가 config 파일이나 프론트엔드 컴포넌트에 시크릿을 하드코딩하는 경우가 빈번합니다.
- **대응:** `.env` 파일 사용, pre-commit hook에 TruffleHog 연동, 노출된 크리덴셜은 즉시 rotate

### 함정 2: 약한 인증 시스템
- AI는 빠른 데모를 위해 인증을 단순화하고, 권한 체크를 클라이언트 측 UI에만 숨기는 경향이 있습니다.
- **대응:** 역할(Role)·권한(Permission)·접근 규칙을 `spec.md`에 먼저 정의하고, **모든 API 엔드포인트에 서버 측 검증** 구현. 경험 있는 엔지니어의 수동 리뷰 필수.

### 함정 3: 검토 없는 의존성 추가
- 빠른 기능 개발 과정에서 AI가 수많은 패키지를 심사 없이 추가합니다 — npm 에코시스템 공급망 공격의 주요 경로.
- **대응:** 의존성 최소화, 모든 추가 패키지 직접 검토, pnpm의 `minimumReleaseAge` 설정, Dependabot 알림 활성화

### 함정 4: 미검증 사용자 입력
- AI는 폼 입력을 "단순한 데이터"로 취급하여 SQL 인젝션·XSS 공격에 무방비 상태를 만듭니다.
- **대응:** 서버 측 스키마 기반 유효성 검사, Parameterized Query, 파일 업로드는 형식·크기(5~10 MB) 제한 및 실제 파일 타입 검사

### 🏁 결론: 2026년형 바이브코딩 표준 워크플로우

> **"느슨한 지시(Vibe)로 시작하되, 엄격한 명세(Spec)와 자동화된 검증(Test)으로 마무리하는 구조"**

바이브코딩은 실제로 프로토타이핑 속도를 극적으로 높여줍니다. 그러나 **"속도 10배"라는 주장은 측정 방법과 맥락에 따라 크게 달라지며**, 실측 데이터는 훨씬 복잡한 그림을 보여줍니다.

진짜 승자는 "도구를 많이 쓰는 팀"이 아닌:
- **언제 AI에 위임하고 언제 직접 개입할지 아는 팀**
- **보안과 스펙을 처음부터 설계에 포함시킨 팀**
- **AI 출력물을 주니어 코드로 대우하고 반드시 검토하는 팀**

입니다.
